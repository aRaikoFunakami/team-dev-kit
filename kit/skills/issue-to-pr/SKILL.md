# Issue → PR パイプライン

1つの Issue を起点に、開発の全工程を順序立てて最後まで通す。**このスキル自体は作業を
再実装しない**。フェーズを並べ、ゲートで判定し、各作業は既存スキルへ委譲するだけ。

`/issue-to-pr #<issue-number>` で起動。引数が無ければ Issue 番号をユーザーに確認する。

## 委譲表（各フェーズの実作業はここへ）

| やること | 委譲先スキル |
|----------|--------------|
| worktree での着手・ブランチ運用・PR 運用契約 | `github-workflow` |
| `work/<feature>/{design,plan,notes}.md` の運用 | プロジェクトの `refactoring-workflow`（無ければ `work/<feature>/` にこの3ファイルを置く） |
| コミット（実装の各ステップ） | `git-commit` |
| PR 発行 | `ticket-pr-publish`（認可済み呼び出し。Phase 7） |
| PR 作成後の自己レビュー | `review-loop`（`/code-review` は周回ごとに新しい子エージェントで実行 → 証拠で判定 → 修正 → 再レビュー。判定・修正は本セッション） |
| Issue 下書き（必要時） | `ticket-draft` / `ticket-publish` |

## 状態

`work/<feature>/plan.md` の先頭に1行だけ持つ:

```
phase: <read|investigate|plan|ready-check|ask-human|implement|accept-gate|pr|review|done>
```

起動時はこの行を読み、記載フェーズから再開する（無ければ read から）。フェーズ完了ごとに更新する。

## フェーズと順序

### Phase 0 — read
`gh issue view #<n>` で Issue を読み、**方針・受け入れ条件（テスト/検証方法）・その他の指摘事項**を
`plan.md` に「合格基準」として転記する。以降この基準は固定し、Phase ready-check と accept-gate で参照する。

### Phase 1 — investigate（調査）
コード・既存実装・依存を調査し、**確定事実だけ**を `notes.md` に積む。推測は書かない。
調査項目は1本のリストで状態管理する:

```
項目状態: 未調査 → { 解決済み | 調査不能(要人間) }
```

**1項目は1回だけ調査する。** 1回で確定できない項目は「調査不能(要人間)」に落とし、再調査しない
（Phase ask-human へ回す）。

#### 根本原因分析（バグ修正・不具合対応系 Issue、`labels: bug` で判定）
「原因」が事象の言い換えになっていないか確認する（現象と原因の混同禁止）。確定事実だけで
「なぜ〜か」を辿り、**仕組み**（テスト・設計・検証プロセスの欠落）に行き着くまで掘り下げる。
回数は目安5回であって固定ルールではない。仕組みに到達したら打ち切ってよいし、事実で答えられない
「なぜ」が出たら通常の調査項目と同じ扱いで即座に「調査不能(要人間)」に落とし、それ以上は
遡らない（再調査しない）。
原因を人（ミス・見落とし）に帰着させない。着地点は仕組み側（例: 該当分岐のテスト不足、
設計漏れ、検証プロセスの欠如）にする。ただし事実として仕組み側の要因が見つからない場合に
それらしい仕組みを捏造しない。事実で裏付けられる仕組み側原因が無ければ、それは「事実で
答えられないなぜ」と同じ扱いで「調査不能(要人間)」に落とす（確定事実だけを積み、推測は書かない規則が優先する）。
候補原因が複数ありうる場合は、原因ごとに別チェーンとして個別に辿る（1本に混ぜない）。
複雑で候補が絞れない場合は、先に候補原因を列挙してから（特性要因図的な整理）、候補ごとに
上記の「なぜ」を適用してよい。

このバグ限定のスコープ（`labels: bug`）は、根本原因分析という概念自体が「不具合の原因究明」
にのみ意味を持つため。次項の証拠への過剰適合防止は原因究明ではなく証拠と仕様の区別なので、
Issue 種別によらず成り立ち、スコープが異なるのは意図的。

### Phase 2 — plan
investigate の確定事実に基づき `design.md`（目的・アーキ・変更点）と `plan.md`（フェーズ分割・TODO）を作る。
バグ修正・不具合対応系 Issue では、`design.md` の変更点に根本原因分析で特定した原因への対策
（仕組み側の再発防止。例: 未カバー分岐への回帰テスト追加）を含める。表面の症状パッチだけを
変更点にしない。

#### 証拠への過剰適合の防止（エビデンス ≠ 仕様、Issue 種別によらず適用）
Issue に添付された再現手順・ログ・特定のテストケースは根本原因を突き止めるための**証拠**であり、
直すべき対象そのものではない（bug Issue に限らず、feature/docs Issue の具体例にも同様に適用する）。
証拠だけに引きずられ「この再現手順・このログ・この1件のテストが通ればよい」という解決策を
設計しない。`design.md` の変更点は、Phase 0 で固定した合格基準（方針・受け入れ条件）という
**一般的な仕様**を満たすことを確認する。
点検観点: 変更点が、証拠になった特定の入力値・ログ文字列・テストケース ID だけを狙った分岐
（ハードコード・特定値判定・その1ケースだけの早期 return 等）になっていないか。なっていれば
「特定ケースだけ通すハック」（特定ケースだけ通す実装はプロジェクトの契約で禁止される）である。この場合の差し戻し（根本原因分析の
書き直し）の回数上限・escalate 先は下記「停止不変条件」の plan ⇄ ready-check エッジに従う
（無制限にはやり直さない）。
（新規着手なので github-workflow の worktree 手順で着手済みであること。未着手ならここで worktree を切る。）

### Phase 3 — ready-check（開発Ready 判定）
`design.md` / `plan.md` / `notes.md` を走査し、次を確認する:
- **推測で埋めた箇所が残っていないか**（未確定は全部炙り出す）
- 調査項目に「未調査」が残っていないか
- バグ修正・不具合対応系 Issue では、原因の記述が事象の言い換えのまま止まっていないか
  （仕組み側の対策に行き着いているか）
- 変更点が、Issue に添付された証拠（再現手順・ログ・特定のテストケース）だけを狙った
  局所パッチになっていないか（Phase 0 の合格基準という一般的な仕様を満たす解決か）

未調査が残っていれば Phase 1 に戻り、**その項目を1回だけ**調査する（未調査集合は毎回必ず減る）。
「調査不能(要人間)」は Phase 1 に戻さず、Phase ask-human へ渡す（Phase 4 は下記の書き直し判定のあと、計画レビューの前に行う）。

原因の記述が言い換えのまま、または証拠への過剰適合が残っていれば Phase 2 に戻り `design.md` を
**1回だけ**書き直す（下記「停止不変条件」の plan ⇄ ready-check エッジ）。書き直し済みかどうかは
`plan.md` に `design.md書き直し: 済` と記録する（記録が無ければ未使用の1回目として扱う）。
書き直し後も解消しなければ implement へは進めず、`plan.md` に「人間確認: design.md要」と明記した
上で Phase ask-human へ escalate する（Phase 4 側でこの記載を拾う。下記参照）。

未調査ゼロ・上記の書き直しも解消済みになったら、`plan.md` に「調査不能(要人間)」または「人間確認: design.md要」が
残っているか確認する。**残っていれば先に Phase 4 を行い**、回答を反映してから次の計画レビューへ進む
（回答前の計画をレビューして1回の枠を使い切らない）。

**計画レビュー**: 文脈を持たない子エージェントに
`design.md` / `plan.md` / `notes.md` と Issue だけを読ませ、合格基準を満たさない箇所・推測で埋めた箇所・
抜けている手順を報告させる（コードの編集は禁止）。報告は候補であって証拠ではないので、呼び出し元が
`review-loop` の判定基準（証拠だけで真/偽/判断不能）で判定し、真の指摘は `design.md` / `plan.md` に反映する。
計画レビューは**1回だけ**（`plan.md` に `計画レビュー: 済` と記録し、再開時も判別する）。反映後も判断不能が
残れば `plan.md` に「人間確認: 計画レビュー要」と記録して Phase ask-human へ escalate し、回答を反映したら
再レビューせずに Ready にする。
子エージェントを使えない環境は同じセッションで実行してよい（独立性が下がることを最終報告に書く）。
計画レビューが済んだら `plan.md` を Ready にする。

### Phase 4 — ask-human（人間確認の要否）
次の3種類の「人間にしか決められない項目」をすべて洗い出す（一部だけ見ない）:
- Phase 1 で「調査不能(要人間)」に落ちた調査項目全件
- Phase 3 で `plan.md` に「人間確認: design.md要」と記録された、design.md 書き直しが
  1回で解消しなかったケース（plan ⇄ ready-check エッジの escalate）
- Phase 3 で `plan.md` に「人間確認: 計画レビュー要」と記録された、計画レビューの判断不能

1件でもあれば `AskUserQuestion` で**一括**確認し、回答を `design.md`（または該当箇所）に
反映し、該当の「人間確認: …要」の記録を「人間確認: 回答済み」に書き換えてから先へ進む（`計画レビュー: 済` でなければ Phase 3 の計画レビューへ、済なら `plan.md` を Ready にして Phase 5 へ。再開時に同じ質問を繰り返さない）。3種類とも0件なら `plan.md` に「人間確認: 不要」と記し素通しする。
**ここが停止点**（該当項目があるときのみ）。

### Phase 5 — implement（実装）
Ready 確定後、1ステップずつ実装するループ（1変更 → 直後に検証 → 次。プロジェクトの AGENTS.md に開発ループがあればそれに従う）を worktree 内で回す。
`plan.md` の TODO を更新しながら進める。各ステップの検証が通るたびに `git-commit` の規約でコミットする。

### Phase 6 — accept-gate（受け入れ検証）
**PR に移る前に**、Phase 0 で固定した合格基準を1件ずつ照合する:
- Issue の方針を満たすか
- 受け入れ条件（テスト/検証方法）を満たすか — 実行コマンドと結果を明示（証拠要件はプロジェクトの AGENTS.md に従う）
- その他の指摘事項を満たすか

未達があれば**原因種別で戻り先を変える**（下記「停止不変条件」）。全基準を満たして初めて Phase pr へ。

### Phase 7 — pr
まず `git status` で追跡対象の未コミット変更が無いことを確認する（未コミットの変更は PR に含まれない。`work/` は通常 gitignore で除外されるためコミット対象に含めない）。次に `gh pr list --head <現在のブランチ> --state open --json number,baseRefName` で既存の PR を確認する。あり、かつ base が default ブランチならそれを使い、発行せずに `phase: review` へ進む（再開時の二重発行を防ぐ）。base が default でなければ停止して報告する。無ければ `/ticket-pr-publish` を**認可済み呼び出し**で呼ぶ。ユーザーが `/issue-to-pr #<n>` を起動した操作を、
その Issue の PR 発行の認可として扱い、呼び出し時に「ユーザーが起動時にこの Issue の PR 発行を認可済み」と
明示する。`ticket-pr-publish` は番号・base・タイトル・リポジトリを提示するだけで同意待ちをせず、そのまま発行する。
発行先・base・本文の決定ルールは `ticket-pr-publish` のまま変えない。発行に成功したら `phase: review` に更新する。**同意では停止しない。** ただし発行そのものが失敗したとき（gh 未認証・push 拒否・issue 番号を抽出できない等）は、黙って Phase 8 へ進まず、`phase: pr` のまま停止して原因をユーザーへ報告する。

### Phase 8 — review（パイプライン終端）
`review-loop` skill に従って自己レビューする（`/code-review` → 証拠で真偽判定 → 真の不具合を全て修正 → 再レビュー）。
レビューは `review-loop` の「実行場所」に従い、**周回ごとに新しい、文脈を持たない子エージェント**で実行する。判定・修正・記録はこのセッションが行う。
子に渡す「意図的な決定の一覧」は、`design.md` の人間確認の結果、Issue の仕様で除外された点、前の周回で偽・対象外と記録した指摘のうち対象のコードが変わっていないもの（PR コメントまたは最終報告の判定記録。再開時はそこを読む。修正で変わったコードの指摘は渡さず、再び報告させる）から作る。
実装の説明や自分の懸念は渡さない。SKILL・ドキュメントだけの変更と、子エージェントを使えない環境は、同じセッションで実行してよい（後者は独立性が下がることを記録と最終報告に書く）。
周回数は `plan.md` の本文（先頭の `phase:` 行ではなく、受け入れ条件ごとの試行回数と同じ記録欄）に `review_rounds: N` として書く。
`phase: review` から再開するときは、この `review_rounds:` を必ず読んで周回数を引き継ぐ。
レビューの前後でユーザーに確認しない（`/code-review` の起動、子エージェントの起動、修正と再レビューは連続実行する）。
真の不具合が 0 件になったら（指摘なし、または全て偽）「review-loop: 指摘なし」と明示し、`phase: done` に更新して、
**最終報告**を出す。最終報告には、PR の URL、合格基準ごとの結果（実行コマンドと出力）、各周回の判定記録、
レビューを実行した場所（子エージェントか同じセッションか）、人間に確認した項目と回答を含める。
`review-loop` の停止条件（周回上限・同一指摘の連続・判断不能）に当たったら、`phase: review` のまま止めてユーザーへ報告する。

**このスキルは Phase 8 で終了する。既定ではマージしない。**
PR をマージ可能な状態にするところまでが本スキルの責務で、マージは既定では人間の判断に委ねる
（3番目の停止点）。パイプラインが自発的に・自然文の勢いで・ゲート通過のついでにマージすることは
**しない**。

**例外: ユーザーがマージを明示依頼した場合のみ**、エージェントは `gh pr merge` を実行してよい。
「マージして」等の明示指示があるときに限り、Phase 8 完了後の独立した操作として扱い、マージ方式
（squash / merge / rebase）は、プロジェクトの AGENTS.md が定めていればそれに従い、無く指定も無ければ確認してから実行する。明示依頼が無い限り自動では
マージしない（＝トリガはあくまでユーザーの明示指示であって、パイプラインの進行ではない）。

## 停止不変条件（無限ループ防止・厳守）

> **どの逆戻りエッジも、有限集合の要素を必ず1つ減らすか、人間ゲート（ask-human / 報告）へ抜ける。
> 同じ項目を同じフェーズへ無条件で差し戻さない。**

具体化:

- **investigate ⇄ ready-check**: 差し戻しは「未調査」項目に対してのみ、1項目1回。1回で確定できなければ
  「調査不能(要人間)」に落として ask-human へ。未調査集合は単調減少するのでループ回数 ≤ 項目数。
- **plan ⇄ ready-check**（原因記述の言い換え／証拠への過剰適合）: 差し戻しは `design.md` の
  書き直しに対して1回だけ。書き直し済みかは `plan.md` の `design.md書き直し: 済` で記録・判定する
  （investigate の notes.md・implement の plan.md 記録と同様、セッション再開後も判別できるようにする）。
  1回で解消しなければ implement へ進めず、`plan.md` に「人間確認: design.md要」と記録した上で
  Phase ask-human へ escalate する（同じ理由で無条件に plan へ差し戻し続けない）。
- **計画レビュー**（Phase 3）: 実施は**1回だけ**。`plan.md` の `計画レビュー: 済` で記録・判定し、
  再開時も判別する。反映後に判断不能が残れば `plan.md` に「人間確認: 計画レビュー要」と記録して
  Phase ask-human へ escalate する（再レビューで差し戻し続けない）。
- **implement ⇄ accept-gate**: 不合格の原因種別で戻り先を変える。
  - A. 実装漏れ/バグ（基準は正しい）→ Phase implement。ただし**同一受け入れ条件の再試行は最大2回**。
    2回連続 fail したら B/C とみなす。試行回数は `plan.md` に基準ごとに記録する。
  - B. 計画・前提が誤り（新たな未確定が発覚）→ implement に戻さず Phase ask-human へ escalate。
  - C. 受け入れ条件自体が達成不能/矛盾 → 停止してユーザーへ報告（Issue 側の問題）。

上限到達・達成不能を検知したら、黙って作り直さず停止して人間へ報告する。

## 停止点まとめ

最後まで連続実行する。PR 発行・レビュー・修正・再レビューでは止まらない。次の点でのみ止まる:
1. Phase ask-human（調査不能(要人間)項目、design.md 書き直し未解消の escalate、計画レビューの判断不能が
   あるときだけ）
2. 上限到達・達成不能時の強制停止（`review-loop` の停止条件、PR 発行の失敗を含む）
3. Phase review 後のマージ（既定はしない＝人間の判断。ユーザーが明示依頼したときのみ、
   Phase 8 完了後の独立操作としてエージェントがマージしてよい。方式未指定なら確認する）
