# レビューループ

レビューの目的は、指摘を並べることではなく、**本当の不具合を PR から無くすこと**。
そのために「レビュー → 証拠に基づく判定 → 修正 → 再レビュー」を、真の不具合が 0 件になるまで繰り返す。

## 1. レビューの実行

- PR レビューも、PR 前のコードレビューも、必ず `/code-review` で行う。
- **渡す引数はレベルと対象（下の「実行場所」）だけにする。** 既定のレベルは `high`（`/code-review high`）。プロジェクトは `AGENTS.md` で変えてよい。
  レベルを渡さないと直前の実行のレベルが使われるため、レベルは毎回明示する。
- `--fix`（判定の前に修正が入る）と `--comment`（判定の前に PR へ投稿される）は使わない。
- 名前空間付きの `code-review:code-review`（プラグイン版）は使わない。PR に自動投稿し、レビュー済み PR をスキップするため、ループが成立しない。
- `/code-review` が使えない環境では、その旨を報告して止まる。代わりの自己判断レビューで進めない。

### 実行場所: レビューは子エージェント、判定と修正は呼び出し元

同じセッションで書いたコードを同じセッションでレビューすると、自分の設計に引きずられて見落とす。
そのため **`/code-review` は、文脈を持たない子エージェント（新しい文脈）に実行させる。**
**判定・修正・記録・`ReportFindings` の再報告は、文脈を持つ呼び出し元が行う。** 判定には、人が決めた事項・Issue の意図・修正の経緯が要るため。

- 子には `/code-review <レベル> <対象>` を実行させる。対象は、PR があるときは PR の URL、PR 前のコードレビューではブランチ名（またはパス）。
  **子が自分でソースを検証した候補だけ**を報告させる。
  子の報告は候補であって証拠ではない。真にするものは、呼び出し元が §2 の証拠で再確認する（子が「検証済み」と書いても、そのまま真にしない）。
- 子に渡すもの: PR と Issue、作業ツリーの場所、読み取り専用の制約（編集・push・PR への投稿・パッケージ導入の禁止）、
  **意図的な決定の一覧**（Issue の仕様で除外された点、人が決めた点、前の周回で「偽」「対象外」と記録した指摘とその根拠。ただし対象のコードが変わっていないものだけ。修正で変わったコードの指摘は再び報告させる）。再報告させないため。
- 子に渡さないもの: 呼び出し元自身の懸念・修正の説明・期待する結論（子の判断が引きずられる）。
- 周回ごとに子を新しくする（前の周回の記憶を持ち越さない）。
- **同じセッションで実行してよい**のは、実行コードを含まない変更（SKILL・ドキュメントだけの PR）と、子エージェントを使えない環境。
  後者は、独立性が下がることを記録と最終報告に明記する。
- 子のレビューは 1 周あたり数万〜10 万トークン・数分かかる。周回上限（§5）とあわせて、上限のある運用として扱う（最悪でも、検証フェーズをはさんで 5 周 + 5 周）。

## 2. 判定: 想像で判定しない

各指摘を **真 / 偽 / 判断不能** のどれかに判定する。

**禁止**: 想像・推測での判定。「〜のはず」「おそらく問題ない」「たぶん誤検知」「普通はこうなる」は、真・偽どちらの理由にもならない。
指摘文に書かれた主張も証拠ではなく、検証する対象として扱う。

### 使える証拠（この 5 種類だけ）

真にも偽にも、少なくとも 1 つを引用して根拠にする。

| 種別 | 内容 | 引用の仕方 |
|------|------|-----------|
| 再現 | Fail するテスト、実行結果、コマンドの出力 | コマンドと出力 |
| ソースコード | 該当箇所、呼び出し元、呼び出し先 | `file:line` |
| 記録 | ログ、CI 結果、git 履歴、仕様書 | 出典と該当行 |
| 設計の定石 | 冪等性、競合状態、リソースリーク、境界での検証、トランザクション境界、エラー伝播など、名前の付いた原則や既知の不具合パターン | 原則名と、コード上の該当箇所 |
| 他分野の同種不具合 | ネットワーク等の同じ構造の既知の障害（タイムアウト未設定、再送・重複、リトライの集中、半開き接続、順序入れ替え、バックプレッシャー、接続断と再接続など） | 一次情報の出典（RFC・公式ドキュメント・仕様の URL と節） |

- 「設計の定石」と「他分野の同種不具合」は、**何が起きうるかの仮説を立てるために使う**。
  真と判定するには、その条件がこのコードで成り立つことを、再現・ソースコード・記録のどれかで示す。
- 偽と判定する場合も同じ。保証している箇所（`file:line`）、通っているテスト、仕様の記述を引用する。
- SSE・WebSocket・非同期処理・外部 I/O に触れる変更では、他分野の同種不具合との照合を特に行う。
- 知識が古い・自信がないときは、調べて出典を付ける。

### 判断不能

証拠が得られない、または調査しても確定できない指摘は **判断不能** にする。真にも偽にも倒さない。
調査は **指摘 1 件につき 1 回まで**。判断不能が 1 件でもあれば人に確認する。
同じ周回に真の不具合もある場合は、**先に真の不具合を修正して反映してから**、判断不能をまとめて確認する。

### 外部調査の作法

- 検索語は一般化した症状に限る。ソースコード、秘密情報、社内の固有名を検索語に含めない。
- 一次情報（RFC、公式ドキュメント、仕様、ライブラリのソース）を優先する。ブログや Q&A は補助にとどめる。
- 外部調査の手段が無い環境では、再現・ソースコード・記録・定石で確定できないものを判断不能とする。

### 記録

指摘ごとに 1 行で残す。**根拠欄が空の記録は無効。**

```
指摘: <何が問題とされたか> / 判定: 真|偽|判断不能 / 根拠の種別: <5 種類のどれか> / 根拠: <file:line・ログ・URL> / 結論: <なぜそう判定したか>
```

記録は PR コメント（`gh pr comment --body-file`）か最終報告に残す。

「同じ指摘」かどうかは、**ファイルと問題の要旨**で判断する（行番号や言い回しが変わっても同じ指摘）。
前の周回で「偽」と記録した指摘が、対象のコードが変わっていないのに再び出た場合は、再調査せず前の記録を引用する。

## 3. 修正

- 修正の対象は **真と判定した、この PR の差分が原因の不具合の全て**。1 件も残さない。
- 範囲外は PR で直さず、別 Issue にする: 既存のバグ、仕様判断、好みの問題。
  簡素化・再利用の提案は不具合ではないので、このループの終了条件に含めない。
- 真の不具合ごとに、Fail→Pass のテストを付ける。付けられない場合は、その理由を記録に書く。
- コミットは `fix(scope): subject` で 1 論点ずつ。「レビュー対応」のような題名にしない。
- 修正後は、`ReportFindings` が使える環境では `outcome` 付きで再報告する。対応は 真 → `fixed`、偽 → `no_change_needed`、判断不能 → `skipped`。
  範囲外の指摘（既存バグ、簡素化・再利用の提案）は修正せず `skipped` とし、記録に「対象外」と書く（既存バグは別 Issue にする）。

## 4. 再レビューと終了

1. 修正を PR に反映（push）したら、再度 `/code-review` を実行する（§1 の実行場所に従い、新しい子エージェントで）。
2. **真の不具合が 0 件** になったら終了する。指摘なし、または全て偽と判定した場合が該当する。
   指摘なしなら「review-loop: 指摘なし」、全て偽なら偽と判定した記録を最終報告に添える。
3. 真の不具合があれば 2 に戻って判定→修正→再レビューを繰り返す。

## 5. 停止条件（無制限実行の禁止）

次のいずれかに当たったら、ループを止めるか、§5a の検証フェーズに入る。止めたら報告し、報告には、残っている指摘と、その判定・根拠、レビューを実行した場所（子エージェントか、同じセッションか）を含める。

- **同じ指摘が 2 周続けて真と判定された**（修正が効いていない）。ユーザーへ報告して止まる。
- **判断不能** の指摘が 1 件でもある（同じ周回の真の不具合を先に修正・反映してから止まる）。ユーザーへ報告して止まる。
- 周回が **5 回** に達した。1 周は「判定 → 修正 → 再レビュー」の 1 セット。5 周目の修正も必ず再レビューし、
  それでも真の不具合が残るなら、§5a の検証フェーズに入る（上限はプロジェクトが `AGENTS.md` で変えてよい）。
  検証フェーズに入った後の周回で再び上限に達したときは、検証をやり直さず、ユーザーへ報告して止まる。
  上の 2 つの即停止（同じ指摘の連続・判断不能）は、検証フェーズの後の周回にも同じように適用する。

## 5a. 検証フェーズ（周回上限に達したとき、1 PR につき 1 回だけ）

上限まで周回しても直らないのは、修正の方向が間違っていることが多い。同じやり方で周回を増やす前に、原因を検証する。
局所的な当て込み（その指摘の行だけを避ける修正、特定の入力だけを通す修正）で通さない。**その分野の王道の設計・修正方針**を採る。

検証は、修正を書いた本人の文脈に引きずられないよう、§1 と同じく **文脈を持たない子エージェント** に行わせ、
結論の判定と報告書は呼び出し元が書く（SKILL・ドキュメントだけの変更と、子エージェントを使えない環境は同じセッションでよい。後者は独立性が下がることを報告書に書く）。

1. **元の修正案を検証する。** 最初に選んだ修正案とその方法が妥当かを、次の面から見る。
   - 根本原因: 指摘は症状か原因か。同じ原因から出る兄弟の呼び出し元・経路が他に無いか。
   - 設計の定石: 該当する原則（冪等性、境界での検証、トランザクション境界、エラー伝播など）に照らして、案の構造は正しいか。
   - 他分野の同種不具合: 同じ構造の既知の障害と、その標準的な解決策（一次情報の出典つき）。
   - 前提と仕様: Issue の意図、人が決めた事項と案が食い違っていないか。
   - 検証可能性: 案が直ったことを示す Fail→Pass のテストを書けるか。書けないなら、案の構造に問題がある。
2. **元の案が誤りなら、そこからやり直す**（3 に進まない）。
3. **元の案が妥当なら、1〜5 周目の修正内容を同じ面から見直す。** 修正の積み重ねが局所的な当て込みになっていないか、
   修正同士が干渉していないか、新たな不具合を生んでいないかを洗い出す。
4. **報告書を書く。** PR コメント（`gh pr comment --body-file`）に残し、プロジェクトに作業メモ置き場（例: `work/`）があればそこにも置く。次を含める。
   - 5 周しても不具合が残る理由（証拠つき）と、元の案の妥当性の判定
   - 1〜5 周目の修正の問題点
   - 選択肢の比較: 「1〜5 周目を取り消して王道の方針でやり直す」「6 周目以降を続ける」のどちらで解決できそうか、その根拠
   - 推奨する方向性と、その確信度
5. **進め方を決める。**
   - **方向性が明確** とは、次の 4 つを全て、§2 の証拠（再現・ソースコード・記録・定石・一次情報）で示せること。
     (a) 不具合が残る根本原因を特定した。(b) 推奨する案が 1 つで、もう一方の案が証拠で否定されている。
     (c) 案が直ったことを示す Fail→Pass のテストを書ける。(d) 人が決めた事項・Issue の仕様と矛盾しない。
     1 つでも示せなければ「明確ではない」。
   - 方向性が明確で、かつ 1〜5 周目に **同じ指摘**（§2 の定義: ファイルと問題の要旨が同じ。連続でなくてもよい）が再び出ていない場合は、報告書の推奨に従って自律で進める。
     取り消してやり直すなら、**`git revert` で打ち消すコミットを積む**（履歴の書き換えと force push はしない。人が決めた事項に基づく変更は取り消さない）。
     続けるなら 6 周目から、通常のループ（§1〜§4）を行う。どちらも **周回数を 0 から数え直し、再び最大 5 回** とする。
   - 明確ではない場合、または同じ指摘が 1〜5 周目に再び出ている場合は、報告書とともにユーザーへ報告し、次の進め方の判断を委ねて止まる。
6. 検証フェーズは 1 PR につき **1 回だけ**。再開後の周回で再び上限に達したら、検証をやり直さず、ユーザーへ報告して止まる。
   検証フェーズに入った事実と、数え直し前の周回数は PR コメントに記録し、再開時に引き継ぐ（issue-to-pr 経由なら `plan.md` の `review_rounds:` を 0 に戻し、`verify_phase: 済` を書く）。

## 6. プロジェクト固有の事項

テストの実行コマンド、証拠の書式、レビューのレベル、周回上限などは、各プロジェクトの `AGENTS.md` に従う。
この skill にはプロジェクト固有の手順を書かない。
