# 文章の書き方（team-dev-kit 管理）

このファイルは team-dev-kit が配布・更新する **文章の共通規則**。プロジェクトは編集しない
（編集しても bootstrap 再実行で置換される。改善は本体リポジトリへ Issue / PR で還元する）。

Issue・PR 本文・設計文書の自然文に適用する。読み手は人間で、言語は契約の `lang` に従う。
AI 向けの圧縮規則（ponytail の「説明を削る」等）は文章には適用しない。短さより、一読で分かることを優先する。

## 1. 読み手を初心者のソフトウェア技術者と想定する

- 読み手はプログラミングと git の基礎は知っているが、このプロジェクトと対象分野は初めてと想定する
- 一般的な技術用語（HTTP、API、JSON、CLI 等）は説明なしで使ってよい
- 分野固有の用語は初出で一文の説明を添える。例: `Appium（モバイルアプリを外部から操作するためのサーバー）`
- 略語は初出で正式名称を示す。英語の正式名称と日本語訳を併記する
  例: `CSR（Certificate Signing Request、証明書署名要求）`
- プロジェクト固有の語も同じ扱い。定義している文書があれば場所を示す
- 筋を追うのに他の文書を開かなくて済むようにする

## 2. 文の組み立て

- 一文に一つの内容。目安は日本語 60 字、英語 20 語
- 括弧の中に文を入れない。補足は次の文に書く
- 理由は括弧に押し込まず、独立した文で書く。仕様の節に理由を書かない規則（ticket-draft）はそのまま。理由は設計判断の節へ
- 箇条書き 1 項目に決定は 1 つ。「〜ので」「〜のため」で複数の決定をつながない
- 3 組以上の対応関係（エラーコードと HTTP ステータス等）は表にする
- 他の Issue / PR を参照するときは、番号だけでなく要点を一文添える
  例: `#226 の仕組み（失敗時にログ末尾を error_message に入れる）を使う`
- 貼るコードは本題に要る行だけにする
- 説明量は内容に応じて変える。重要な判断には行を割き、自明な箇所は短く済ませる

## 3. 書かないこと

- 入力に無い事実。推測した仕様・バージョン・API は書かず「不明」または「（未確定）」と書く
- 根拠のない評価語。程度を言うときは数値か比較条件を添える
  例: 「大幅に遅い」ではなく「Playwright MCP 比で 447 秒/ステップ遅い」、「堅牢なループ」ではなく何に対して壊れないかを書く
- 水増し: 同じ内容の言い換え、一度説明したことの繰り返し、コードから自明な処理の説明、API 名を日本語に言い換えただけの説明
- 装飾: 太字の乱用、絵文字、必要のない表・リスト
- 読者への語りかけと定型句: 「見ていきましょう」「ここがポイントです」「安心してください」
- 架空の体験や感情: 「試してみた」「ハマった」「経験上」

## 4. 事実と判断の書き分け

- 事実と推測を混ぜない。推測は推測と分かる書き方にする
- 判断には根拠を書く。比較があれば比較条件を、不採用案があれば不採用の理由を書く
