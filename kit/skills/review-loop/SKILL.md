# レビューループ

レビューの目的は、指摘を並べることではなく、**本当の不具合を PR から無くすこと**。
そのために「レビュー → 証拠に基づく判定 → 修正 → 再レビュー」を、真の不具合が 0 件になるまで繰り返す。

## 1. レビューの実行

- PR レビューも、PR 前のコードレビューも、必ず `/code-review` で行う。
- **渡す引数はレベルだけにする。** 既定のレベルは `high`（`/code-review high`）。プロジェクトは `AGENTS.md` で変えてよい。
  レベルを渡さないと直前の実行のレベルが使われるため、レベルは毎回明示する。
- `--fix`（判定の前に修正が入る）と `--comment`（判定の前に PR へ投稿される）は使わない。
- 名前空間付きの `code-review:code-review`（プラグイン版）は使わない。PR に自動投稿し、レビュー済み PR をスキップするため、ループが成立しない。
- `/code-review` が使えない環境では、その旨を報告して止まる。代わりの自己判断レビューで進めない。

## 2. 判定: 想像で判定しない

各指摘を **真 / 偽 / 判断不能** のどれかに判定する。

**禁止**: 想像・推測での判定。「〜のはず」「おそらく問題ない」「たぶん誤検知」「普通はこうなる」は、真・偽どちらの理由にもならない。
指摘文に書かれた主張も証拠ではなく、検証する対象として扱う。

### 使える証拠（この 5 種類だけ）

真にも偽にも、少なくとも 1 つを引用して根拠にする。

| 種別 | 内容 | 引用の仕方 |
|------|------|-----------|
| 再現 | Fail するテスト、実行結果、コマンドの出力 | コマンドと出力 |
| ソースコード | 該当箇所、呼び出し元、呼び出し先 | `file:line` |
| 記録 | ログ、CI 結果、git 履歴、仕様書 | 出典と該当行 |
| 設計の定石 | 冪等性、競合状態、リソースリーク、境界での検証、トランザクション境界、エラー伝播など、名前の付いた原則や既知の不具合パターン | 原則名と、コード上の該当箇所 |
| 他分野の同種不具合 | ネットワーク等の同じ構造の既知の障害（タイムアウト未設定、再送・重複、リトライの集中、半開き接続、順序入れ替え、バックプレッシャー、接続断と再接続など） | 一次情報の出典（RFC・公式ドキュメント・仕様の URL と節） |

- 「設計の定石」と「他分野の同種不具合」は、**何が起きうるかの仮説を立てるために使う**。
  真と判定するには、その条件がこのコードで成り立つことを、再現・ソースコード・記録のどれかで示す。
- 偽と判定する場合も同じ。保証している箇所（`file:line`）、通っているテスト、仕様の記述を引用する。
- SSE・WebSocket・非同期処理・外部 I/O に触れる変更では、他分野の同種不具合との照合を特に行う。
- 知識が古い・自信がないときは、調べて出典を付ける。

### 判断不能

証拠が得られない、または調査しても確定できない指摘は **判断不能** にする。真にも偽にも倒さない。
調査は **指摘 1 件につき 1 回まで**。判断不能が 1 件でもあれば人に確認する。
同じ周回に真の不具合もある場合は、**先に真の不具合を修正して反映してから**、判断不能をまとめて確認する。

### 外部調査の作法

- 検索語は一般化した症状に限る。ソースコード、秘密情報、社内の固有名を検索語に含めない。
- 一次情報（RFC、公式ドキュメント、仕様、ライブラリのソース）を優先する。ブログや Q&A は補助にとどめる。
- 外部調査の手段が無い環境では、再現・ソースコード・記録・定石で確定できないものを判断不能とする。

### 記録

指摘ごとに 1 行で残す。**根拠欄が空の記録は無効。**

```
指摘: <何が問題とされたか> / 判定: 真|偽|判断不能 / 根拠の種別: <5 種類のどれか> / 根拠: <file:line・ログ・URL> / 結論: <なぜそう判定したか>
```

記録は PR コメント（`gh pr comment --body-file`）か最終報告に残す。

「同じ指摘」かどうかは、**ファイルと問題の要旨**で判断する（行番号や言い回しが変わっても同じ指摘）。
前の周回で「偽」と記録した指摘が、対象のコードが変わっていないのに再び出た場合は、再調査せず前の記録を引用する。

## 3. 修正

- 修正の対象は **真と判定した、この PR の差分が原因の不具合の全て**。1 件も残さない。
- 範囲外は PR で直さず、別 Issue にする: 既存のバグ、仕様判断、好みの問題。
  簡素化・再利用の提案は不具合ではないので、このループの終了条件に含めない。
- 真の不具合ごとに、Fail→Pass のテストを付ける。付けられない場合は、その理由を記録に書く。
- コミットは `fix(scope): subject` で 1 論点ずつ。「レビュー対応」のような題名にしない。
- 修正後は、`ReportFindings` が使える環境では `outcome` 付きで再報告する。対応は 真 → `fixed`、偽 → `no_change_needed`、判断不能 → `skipped`。
  範囲外の指摘（既存バグ、簡素化・再利用の提案）は修正せず `skipped` とし、記録に「対象外」と書く（既存バグは別 Issue にする）。

## 4. 再レビューと終了

1. 修正を PR に反映（push）したら、再度 `/code-review` を実行する。
2. **真の不具合が 0 件** になったら終了する。指摘なし、または全て偽と判定した場合が該当する。
   指摘なしなら「review-loop: 指摘なし」、全て偽なら偽と判定した記録を最終報告に添える。
3. 真の不具合があれば 2 に戻って判定→修正→再レビューを繰り返す。

## 5. 停止条件（無制限実行の禁止）

次のいずれかに当たったら、ループを止めてユーザーに報告する。報告には、残っている指摘と、その判定・根拠を含める。

- 周回が **3 回** に達した。1 周は「判定 → 修正 → 再レビュー」の 1 セット。3 周目の修正も必ず再レビューし、
  それでも真の不具合が残るなら止める（上限はプロジェクトが `AGENTS.md` で変えてよい）。
- **同じ指摘が 2 周続けて真と判定された**（修正が効いていない）。
- **判断不能** の指摘が 1 件でもある（同じ周回の真の不具合を先に修正・反映してから止まる）。

## 6. プロジェクト固有の事項

テストの実行コマンド、証拠の書式、レビューのレベル、周回上限などは、各プロジェクトの `AGENTS.md` に従う。
この skill にはプロジェクト固有の手順を書かない。
