本 skill はローカルにファイルを作るだけ（GitHub へは登録しない）なので自動起動を許容する。
-->

会話または開発計画から GitHub Issue 下書きを **AI が生成** する（1 件でも N 件でも可）。手順を厳守する。

1. **作業項目の抽出**
   - `$ARGUMENTS` で計画ファイル（例 `@PLAN.md`）が渡された場合、先頭の `@` を除いて読み込み、対象に含める。
   - 引数が無ければ、その時点までの会話内容から作業項目を抽出する。
   - 抽出した作業項目を番号付きリストで提示する（1 項目 = 1 下書き）。

2. **種別の割当（一括確認）**
   - 各項目に種別 **bug / docs / feature** を自動推定して割り当てる。
   - 推定した「項目 → 種別」の対応表を提示し、`AskUserQuestion` で一括確認・修正を取る。
     項目数が多くても、まとめて 1 回で確認する（項目ごとに N 回聞かない）。

2'. **検証単位（feature）の確定**
   - 抽出項目のうち「単体で E2E 検証できないもの」を検出し、**同じ E2E シナリオで検証される
     項目を 1 つの feature にグルーピング** する。
   - 「項目 → 種別 + feature」の対応表を提示し、手順 2 の `AskUserQuestion` で種別と一括確認する
     （項目ごとに N 回聞かない）。
   - 各下書きの「検証単位」節に feature 名を 1 行記載する（単体なら `単体`）。
     **兄弟 Issue は列挙しない**（メンバーの SSOT は EPIC/トラッキング Issue の task-list か
     `work/<name>/plan.md`。子 Issue は所属先を指す 1 行のみ）。
   - N≥2 の feature には、メンバーを束ねる SSOT（トラッキング Issue の task-list 推奨）を 1 つ用意する。

3. **下書きの生成**
   - 保存先 timestamp を `date +%Y%m%d-%H%M%S` を Bash で 1 回取得し、全項目で共有する。
   - 各項目の保存先を `.issue_drafts/<type>-<timestamp>-NN.md` とする
     （`NN` は項目連番 `01, 02, …`。同一 timestamp 内で連番により衝突回避）。`.issue_drafts/` が無ければ作る。
   - 各項目について、割り当てた種別のテンプレを読む:
     - bug → `.github/ISSUE_TEMPLATE/bug.md`
     - docs → `.github/ISSUE_TEMPLATE/docs.md`
     - feature → `.github/ISSUE_TEMPLATE/feature.md`
   - テンプレ構造（節・見出し）に沿って各下書きを作成する。テンプレは spec-first
     （目的 → 仕様 → 変更対象 → 受け入れ条件 → 設計判断 → 背景 → …）。**節順は変えない**:
     - **frontmatter** はテンプレからそのままコピーする（発行時に title/label を拾うため残す）。
       ただし `title:` はその項目を要約した具体的なものに置き換える。
       本文のプレースホルダ（`<issue-number>` 等）は残さない。
     - **タイトル規約**（title の値）:
       - `type(scope):` の接頭辞を付けない。種別はテンプレ由来のラベルが表す。
       - 契約の `lang` の言語で、接頭辞なしの一文にする。バグは「条件＋症状」、機能は「できるようになること」、docs は「どの文書に何を足す / 直す」。
       - 変更対象を **名指し** する（関数 / API / モジュール名）。`内容取得ツール` のような
         抽象語、`cap` のような曖昧語は使わない（必要なら `200文字cap` と具体化する）。
       - **「何を変えるか」だけ** を書く。手段と目的（なぜ）を混ぜない。目的は本文の「目的」節へ。
       - 日本語 40 字、英語 70 字を目安にする。
     - **本文の文章** は `.team-dev-kit/writing.md` に従う（読み手は初心者のソフトウェア技術者。
       略語は初出で正式名称、一文に一つの内容、括弧に文を入れない、3 組以上の対応は表、参照には要点を添える）。
     - **本文** は会話/計画にある **確定事実だけ** で各節を埋める。会話/計画に無い情報は捏造しない。
       不明・未確定の節は推測で埋めず `（未確定）` 等の明示プレースホルダを置く。
     - **節の役割を混ぜない**（LLM が仕様を推論なしで抽出できるようにする）:
       - `仕様` = テスト可能な実装要求のみ（API/引数/返却/例外）。「なぜ」を書かない。
       - `設計判断` = 採用理由の箇条書きのみ。比較・代替案の詳細は書かず PR/ADR へ回す。
       - `背景` = 今回必要な理由だけ、**3〜5 行**。経緯の詳細は設計メモ/ADR へ。
       - `受け入れ条件` = テスト可能な結果のみ。**仕様の再掲をしない**。
       - 同じ節に「仕様」と「理由」を混在させない。長い監査/調査結果は `調査結果` 節へ寄せる。

4. **機密情報・個人情報の扱い**
   - 会話/計画に機密情報・個人情報（トークン/鍵/メール/個人名等）が含まれる場合、
     下書きへ転記する **前に** 指摘し、マスキング・除外する。

5. **出力**
   - エディタでは開かない。`pwd` 等で絶対パスを得て、生成した **全下書きの絶対フルパス一覧** を出力する
     （Claude Code 上でクリックすれば開ける）。
   - 各下書きの要点を簡潔に提示し、「各々 `/ticket-publish @<path>` で個別に発行する」と案内する。
     一括発行は誤起票リスクが高いため本 skill には含めない（発行は `/ticket-publish`）。

注意:
- 本文は会話/計画ベースで生成する。会話/計画に無い情報は捏造しない。確証の無い節は明示プレースホルダにする。
- 最終確認・編集はユーザーが行う前提。生成は下書きであり発行ではない。
- 既存の同名ファイルは上書きしない（timestamp + 連番で衝突回避済み）。
- job は「本文を誰が書くか」で分ける。**手で書く下書きの足場が欲しいだけなら `/ticket-template`**、
  会話/計画から本文を起こすなら本 skill（1 件でも可）。発行は `/ticket-publish`。
